## 一、摘要

**devnpc** 是一款基于 GitLab 的企业级研发流程 AI 智能体,定位为"研发侧的 CodeBuddy NPC"。它监听研发协同平台(Issue/MR)中的任务指令,在 CI 环境内自主完成"理解上下文 → 修改代码 → 提交验证 → 跟踪 CI → 修复失败"的全闭环工作,把人力从重复性研发运维劳动中解放出来,让研发聚焦在创造性问题上。

当前已完成核心 Agent 引擎(P0–P3),具备端到端的 LLM ↔ 工具调用循环能力,**110 个单元测试全部通过,零静态检查警告,Release 版本可编译运行**。

## 二、背景与痛点

### 2.1 现状痛点

在企业级研发协同中,以下场景长期占用研发大量时间:

| 场景 | 痛点 | 影响 |
|------|------|------|
| **CI 失败修复** | 提交后 CI 报错,需人工排查日志、定位根因、改码重提 | 阻塞集成,等待时间长 |
| **重复性 Issue 处理** | 简单 bug、文档修正、依赖升级等机械任务 | 占用高价值工程师时间 |
| **跨上下文切换** | 修一个 bug 需翻阅 Issue、PR 历史、代码、CI 日志 | 上下文重建成本高 |
| **夜间/休假响应** | 非工作时间 CI 失败无人处理 | 拖延交付节奏 |
| **研发规范落地难** | 编码规范、检查清单靠人记忆 | 规范执行不到位 |

### 2.2 期望目标

构建一个**7×24 在线、可监督、可审计**的 AI 研发助手,具备以下能力:

1. **自主执行**:收到任务后独立完成代码修改与验证,无需人工介入
2. **安全可控**:所有操作在沙箱内,遵守项目规范,有完整执行轨迹
3. **闭环修复**:CI 失败能自动定位根因并修复,支持有限次重试
4. **可观测**:每次任务生成运维报告,便于复盘与审计
5. **可扩展**:支持多角色 NPC(开发/测试/运维)协同处理复杂任务

## 三、系统定位与价值

### 3.1 系统定位

devnpc **不是**通用的代码生成工具,而是**嵌入研发流程的执行型 Agent**:

```
┌────────────────────────────────────────────────────────────┐
│  传统研发流程:                                             │
│  Issue → 人工分析 → 人工改码 → 人工提交 → CI 验证 → 人工修复 │
│                                                            │
│  devnpc 赋能后的流程:                                       │
│  Issue → @devnpc → AI 自主改码+提交+验证+修复 → 人工 Review │
└────────────────────────────────────────────────────────────┘
```

**关键差异**:把"人执行"变为"AI 执行+人审核",人只在关键决策点介入。

### 3.2 核心价值

| 维度 | 价值 |
|------|------|
| **降本** | 机械性研发任务(简单 bug、文档、依赖升级)由 AI 承担,估算可释放研发 15%–25% 工时 |
| **提效** | CI 失败从"小时级等待"压缩到"分钟级自动修复",集成节奏显著加快 |
| **全天候** | 7×24 响应,夜间/休假 CI 失败不再阻塞次日交付 |
| **规范落地** | 项目编码规范、检查清单以 SOP 形式注入 Agent,执行一致性 100% |
| **可审计** | 完整执行轨迹 + 运维报告,每次任务可追溯、可复盘 |
| **低侵入** | 复用现有 GitLab 工作流,不改变研发使用习惯,仅在评论中 `@devnpc` 即可触发 |

### 3.3 适用场景

- **CI 修复闭环**:MR 提交后 Pipeline 失败,devnpc 自动分析日志、定位根因、改码重提
- **简单 Issue 自助处理**:标签为 `npc-suitable` 的简单 bug/文档任务由 devnpc 接手
- **批量机械任务**:依赖升级、API 重命名、日志格式统一等批量改动
- **新成员辅助**:新成员提交 MR 后,devnpc 自动 Review 规范问题并给出修复建议
- **夜间值守**:非工作时间自动处理 CI 失败,次日上午研发直接 Review 已修复的 MR

## 四、技术方案与创新点

### 4.1 总体架构

采用**三层混合架构**,兼顾灵活性与可控性:

```
┌─────────────────────────────────────────────────────────────┐
│  接入层  trigger  ← @devnpc 提及解析 + Webhook               │
├─────────────────────────────────────────────────────────────┤
│  智能层  ┌─────────────────────────────────────────────┐    │
│         │  memory   研发记忆聚合(Git+Issue+PR+CI)      │    │
│         │  agent    ReAct 循环 + SOP 双层约束           │    │
│         │  npc      多角色(开发/测试/运维)+ 编排       │    │
│         └─────────────────────────────────────────────┘    │
├─────────────────────────────────────────────────────────────┤
│  执行层  ┌─────────────────────────────────────────────┐    │
│         │  tools    8 自建工具 + 5 AST 代码工具         │    │
│         │  ci       Pipeline 闭环控制器                │    │
│         │  report   轨迹采集 + HTML 报告               │    │
│         └─────────────────────────────────────────────┘    │
├─────────────────────────────────────────────────────────────┤
│  基础层  config(三层合并) + gitlab_api + git + error       │
└─────────────────────────────────────────────────────────────┘
```

**分层职责**:
- **接入层**:解析触发指令,不承担业务逻辑
- **智能层**:决策中心,负责理解任务、规划步骤、调度执行
- **执行层**:唯一副作用出口,所有写操作集中,便于审计与沙箱化
- **基础层**:配置、API 客户端、错误处理等基础设施

### 4.2 关键技术选型

| 决策点 | 选型 | 理由 |
|--------|------|------|
| **开发语言** | Rust | 内存安全、零成本抽象、编译期错误检查,适合长期运行的可靠 Agent |
| **异步模型** | tokio | 成熟的 async/await 实现,支持超时、并发、子进程 |
| **LLM 调用** | reqwest 直连 OpenAI 兼容 API | MVP 阶段单 provider 即可,可控可测;后期引入 rig-core 支持多模型路由 |
| **代码感知** | tree-sitter + agent-file-tools | AST 级代码操作,显著降低 token 消耗,支持大文件 |
| **Agent 范式** | 自建 ReAct 循环(Plan-Act-Observe) | 相比框架黑盒,自建循环可完全控制迭代逻辑、SOP 约束、轨迹记录 |
| **配置体系** | env > .devnpc.md > 默认值 三层合并 | 适应 CI/本地/不同项目多种环境,项目级规范随仓库走 |
| **报告渲染** | askama 编译期模板 | 无运行时模板引擎开销,HTML 报告零依赖部署 |

### 4.3 创新点

#### 创新点 1:SOP 双层约束机制(方案 C 核心)

业内多数 Agent 仅靠 prompt 软约束行为,devnpc 引入**SOP(标准作业程序)双层约束**:

- **Soft 模式**(已实现):Agent 偏离预定步骤时,只在轨迹中记录警告,下轮提示 LLM 回归
- **Strict 模式**(规划中):偏离即阻断执行,强制人工介入

**价值**:把"研发规范"从文档变成可执行约束,确保 Agent 行为可预测、可审计。

#### 创新点 2:研发记忆聚合

任务执行前,devnpc 主动聚合多源上下文:

- **Git 仓库树**:`git ls-tree` 解析目录结构(二级展开,平衡细节与 token)
- **关键文件摘要**:自动识别 Cargo.toml/README/入口文件并摘要
- **Issue/PR 历史**:目标 Issue + 相关 PR + 评论记录
- **CI 失败记录**:最近 Pipeline 失败根因

**价值**:避免 LLM "凭空臆测",所有决策基于真实研发上下文,显著提升修改准确性。

#### 创新点 3:沙箱化工具系统

所有副作用操作走统一的 `Tool` trait,内置多层安全:

- **路径越界检查**:`read_file`/`write_file` 防 path traversal
- **命令白名单**:`run_command` 仅允许 cargo/rustc/make 等构建工具,禁用 rm/curl/wget
- **超时控制**:默认 120s,防止恶意/死循环命令
- **分支保护**:禁止操作主分支,强制走 MR 流程

**价值**:Agent 在生产环境安全运行,不会误删代码或泄露敏感信息。

#### 创新点 4:CI 闭环自动修复(规划中)

CI 失败时,devnpc 自动完成"日志解析 → 根因定位 → 代码修复 → 重新提交 → 跟踪验证"闭环,支持 `max_ci_retries` 次重试。

**价值**:把研发从"CI 失败等待-修复-再等待"的循环中彻底解放。

#### 创新点 5:多角色 NPC 协同(规划中)

支持不同角色 NPC(开发/测试/运维)通过 GitLab 评论总线协同,复杂任务由编排器拆分调度。

**价值**:突破单 Agent 能力边界,处理跨领域复杂任务。

### 4.4 与同类产品差异

| 维度 | 通用 AI 编程助手 | devnpc |
|------|------------------|--------|
| **定位** | 辅助编码(人在环) | 自主执行(人在审核环) |
| **触发** | IDE 内手动调用 | GitLab 平台自动触发 |
| **上下文** | 单文件/局部 | 全仓库 + Issue/PR/CI 多源聚合 |
| **闭环** | 仅生成代码 | 改码 → 提交 → CI 验证 → 修复全闭环 |
| **规范** | 无强制约束 | SOP 双层约束 + 项目规范注入 |
| **审计** | 无 | 完整轨迹 + 运维报告 |
| **协作** | 单人 | 多角色 NPC 协同 |

**P4(CI 闭环)**:实现 CI 失败 → 日志解析 → 根因定位 → Agent 修复 → 重新提交 → 跟踪验证的完整闭环,这是 devnpc 最核心的业务价值场景,也是后续推广的卖点。

## 七、风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| LLM 调用成本 | 高频任务 token 消耗大 | P3.5 AST 工具省 token;P8 模型分级路由,简单任务用小模型 |
| Agent 误改代码 | 引入新 bug | 沙箱工具系统 + SOP 约束 + 强制 MR 流程(人审核) |
| 多语言支持 | tree-sitter grammar 覆盖度 | 优先支持 Rust/Go/Python/Java,其余语言回退到按行读写 |
| 生产环境安全 | Agent 权限过大 | 命令白名单 + 路径越界检查 + 分支保护 + 完整审计轨迹 |

## 八、总结

devnpc 定位为**研发流程的自主执行型 AI Agent**,核心价值在于把研发从机械性、等待性劳动中解放,让人聚焦创造性工作。

当前已完成核心 Agent 引擎(P0–P3),具备了 LLM ↔ 工具调用的端到端闭环能力,工程基础扎实(110 测试、零警告、Release 可用)。下一阶段将重点突破 **CI 闭环自动修复**(P4),这是最直接的业务价值场景,也是推广的关键卖点。
